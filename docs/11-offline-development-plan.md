> 厂商接入路线与第一阶段完成标准以 [需求文档](01-requirements.md#厂商接入路线与第一阶段完成标准) 为准。本文先列当前推进重点，后续章节保留汇川阶段内各开发批次的实现范围；批次编号不代表厂商接入阶段。运行基础见 [交付说明](21-delivery-closure.md)，当前实现与限制见 [工具清单](22-current-tools.md) 和 [能力缺口](23-capability-closure.md)。

本阶段先完成可独立开发的 PLC MCP 服务、汇川适配器和官方 API 调用脚本，并通过自动测试验证服务流程。目标 InoProShop 的兼容性与真实工程验收安排在取得 Windows 环境之后，不作为当前开发的前置条件。

当前已合入主线的实现批次为 P11，候选版本 `0.1.0-rc.2`。Mac 可以继续离线开发和测试；真实汇川工程验收需要后续目标 Windows/InoProShop 环境。当前实现包括组态、XML 与 graph-v1/v2、批量、大文件、增量编程、成员编辑、交付与图形聚合初值。复杂图形、CFC 结构化编辑与 PDO 仍保留明确缺口，详见 [当前功能范围](23-capability-closure.md)。

## 当前基线与产品边界

已有 .NET 8 核心架构、74 个 MCP 工具实现、汇川适配器与原创脚本、持久化调度、受控副本与版本恢复，以及 Windows/Linux/macOS 自动检查。正式宿主无真实验收记录时开放 22 个本地工具；OpenCode CLI 连接已有 CI 检查，真实模型编程与 InoProShop 工程闭环尚未验收。证据与验证边界见 [当前候选验证基线](07-validation.md#当前候选验证基线p11)。

继续采用 .NET 8、DDD 与模块化单体。对外只有本项目的 PLC MCP Server，汇川模块通过内部端口与执行协议调用 ScriptEngine。增加厂商主要增加适配器和版本执行器。当前不建设通用 MCP 服务接入/托管/聚合平台、模型网关或 Agent 编排框架。

生产用例、执行器和厂商脚本是交付主体。测试替身只作为自动测试依赖，不替代厂商适配器，也不产出冒充 InoProShop 工程的文件。

## 第一批 任务执行与工程读取编译

本节保留第一批开发范围；已完成离线实现，完成状态与验证证据见执行实现说明。

| 顺序 | 开发工作 | 交付物 | 无 IDE 验收标准 |
|---|---|---|---|
| A1 | 固定工程操作和 Worker v1 契约 | 输入/输出 Schema、错误语义、任务结果、契约样例；更新 Contracts 与 docs/06 | 非法输入、版本不匹配、错误任务关联和超限结果被拒绝；截断与部分结果显式表达 |
| A2 | 实现持久化任务调度 | SQLite 迁移与 Store、Channel 唤醒、状态持久化、单实例所有权与 IDE 串行调度 | 入库后通知丢失仍可恢复；重复请求不重复执行；取消、重启和结果未知符合状态规则 |
| A3 | 实现汇川执行边界 | .NET 进程执行器、配置、版本策略接口、受控脚本入口、请求/结果传递及超时处理 | 用独立测试进程验证真实进程通信、退出、超时、损坏结果、关联 ID 和日志隔离 |
| A4 | 编写第一组原创脚本 | 工程打开、对象树读取、POU 声明/实现读取、指定 Application 编译与本次诊断采集 | 依据 CHM/官网实现实际调用；用测试替身检查参数、对象选择、异常映射和诊断范围；不将替身编译视为真实编译 |
| A5 | 接入 MCP 与跨平台检查 | 四个工程工具、三个任务工具、专用测试宿主、macOS CI、开发说明 | 通过 HTTP MCP 完成提交、轮询和取结果；Windows/Linux/macOS 跑平台测试，不依赖供应商软件 |

A2 首期按一个服务实例、一个受控 IDE 执行槽实现，使用数据库约束和实例所有权防止重复领取。不扩展成通用分布式调度平台。服务重启时，排队任务可恢复；执行中任务进入结果待确认，不直接重放。相关工程/执行槽必须完成对账或确认隔离后才可继续，不能只修改任务状态就继续写入。

A3 保留内部版本化 JSON 协议，先实现可测试的进程请求/结果边界与每任务隔离目录；工程脚本不提供 HTTP/MCP 服务。执行器只启动配置的 IDE 与白名单操作脚本，不提供任意命令或任意 Python 工具。实际 InoProShop 启动参数、Profile、无 UI 与结果传递适配由版本策略承接，先按官方资料实现，兼容性留待验证。取消只有在确认本任务执行已停止后才能完成，不能因为取消 HTTP 请求就认为 IDE 已停止。

第一批工具清单如下；工具与请求 Schema 在 A1 一并固定。

| 工具 | 目标行为 |
|---|---|
| `plc_project_open` | 校验允许的工作区路径，建立工作区上下文并提交受控打开任务 |
| `plc_project_get_structure` | 返回对象标识、父子关系及截断信息 |
| `plc_pou_read` | 返回声明、实现及对应修订；不把图形网络伪装为文本实现 |
| `plc_project_compile` | 针对指定 Application 提交编译，返回本次诊断；不用退出码代替编译结论 |
| `plc_job_get` | 查询任务状态 |
| `plc_job_cancel` | 请求取消并区分请求已受理与执行已停止 |
| `plc_job_get_result` | 查询结果、错误及部分完成情况 |

第一批完成意味着工程读取/编译调用流程和相应实现可接受离线开发验收，尚不表示可以生成或编译真实汇川工程。

## 第二批 程序生成修改与保存

已完成本批离线实现，具体工具、启动方法、版本语义与恢复限制见 [第二批交付](13-managed-editing.md)。以下保留该批目标，不作为真实 IDE 支持声明。

在第一批执行边界上实现 `plc_project_create`、`plc_project_save`、`plc_pou_create/update` 以及 GVL/DUT 操作。工程创建优先提供目标模板复制路径，模板、设备和库依赖由配置描述，缺少依赖时返回明确错误，不生成虚构的厂商工程包。

交付完整的修改用例：读取当前内容与修订、生成修改请求、检查工作区与 IDE 会话状态、备份、执行、读回、保存、记录新修订和结果。文件哈希不能替代未保存的 IDE 会话状态检查。多对象修改可能部分成功，必须记录已完成步骤与备份位置；数据库回滚不能宣称工程已回滚。

新增写入脚本必须包含官方 API 调用与结果处理，不以空接口或恒定成功返回作为完成。自动测试至少覆盖重复写请求、同键不同内容、修订冲突、保存失败、执行后断连和恢复判断。测试环境内可以跑“读取—修改—模拟诊断—修复”的完整工具流程，每个结果保留测试来源。

任务与 POU 的调用绑定作为程序交付条件单独验证。编译通过不能替代任务绑定检查，更不能作为 PLC 运行正确的证明。

## 开发模式与生产支持声明

默认真实模式不自动切换到模拟执行。没有 IDE 的环境查询仍返回未连接、`engineeringReady=false`；未验证的工程工具不向生产客户端注册。已通过版本验证的能力若在运行时失去 IDE 等前提，应用用例返回 `ide_unavailable` 等明确错误，不返回伪造的工程/编译成功。

测试宿主与真实模式分别启动，使用独立配置和数据目录。测试替身不进入默认生产依赖注册。测试宿主可注册待验收的同契约工具，用于 HTTP 和 OpenCode 接入验证，状态与每次工具结果均显式包含测试执行来源。测试结果中的成功只表示测试场景按预期结束，不更新汇川能力为 `Supported`。

每个能力分别报告以下进展，不能以一个百分比替代：

| 维度 | 完成含义 |
|---|---|
| 实现进度 | 实际业务用例、适配器与脚本已编写；没有以空壳代替功能 |
| 自动测试 | 契约、调度、进程通信和对应脚本调用逻辑通过自动检查 |
| 厂商验证 | 在记录了版本、Profile、设备/库与样例的真实 IDE 中执行通过 |

生产能力仅由第三项的限定范围验证决定。接口可见或自动测试通过不等于厂商验证通过。
